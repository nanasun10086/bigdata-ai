大模型的上下文（Context）

为什么模型"记不住"上次聊天？为什么文件太长塞不进？为什么叫"上下文窗口"？——一次讲清大模型"看得见什么、记到哪"这件事。

上下文窗口TokenAttention记忆

01个人解释 Personal Explanation

一句话：大模型的"上下文"= 它当下这一轮能"同时看到并依赖"的全部文字，放不进去的它看不见。 想象一个有超强阅读力但极短"桌面"的专家：你把一份材料放上桌，他读得又快又准；但桌面只有那么大，摆不下的文件他就根本看不到，更别提记住桌外早先放过的东西——除非你帮他归档成笔记再放回桌上。

聊天里的"上下文"常指三样东西叠在一起：系统设定（你是谁、怎么回答）+ 多轮对话历史（你和它前面聊了啥）+ 当前输入/附加资料（刚发的话、粘贴的文件）。模型每次生成都把这些"一次性喂进去"，因此：它不是"记"住的，而是每一轮都重新"读"一遍全部上下文再作答。

一个生活化类比 🧠

把大模型想象成一位读过一次就忘、但每次都能重新看笔记的考生。你每次问他，都得把"要考的笔记"摆在他眼前（塞进上下文）。他的"短期笔记夹"（上下文窗口）就那么大——装不下的页数会被裁掉。至于"上次他记住的你"，其实靠的是你把聊天记录逐字叠回去，他并没有独立的长时记忆。

个人倾向（可讨论）：把"上下文"和"记忆"当成两件事，是理解大模型产品设计的关键。厂商宣传"百万上下文"很诱人，但塞得进 ≠ 用得准——超长上下文常伴随"中间内容被稀释"（lost in the middle）与更高成本。真正聪明的工程是少塞、塞对、分层记忆，而不是一味把东西都堆进上下文。

02核心机制 Core Mechanism

上下文之所以存在上限，根子在 Transformer 的 Attention（注意力）机制：模型要让上下文里任意两个词都能"互相看"，每轮计算的注意力量大致随输入长度平方增长（O(n²)）。所以"上下文窗口"是模型在参数量、显存/算力、精度之间权衡出的可承载文本上限。

计量单位：Token（词元）

窗口不是按"字数/字符"算，而是按 Token 算。Token 是模型处理文本的最小单元，可粗略理解为"半个到一个词"。例如"大模型的上下文"可能被切成若干个 token。中文下 1 个汉字常约合 1~2 token。各家模型"窗口"如 8K / 128K / 1M（如 GPT-4o 系列、Claude、Gemini 的 1M+），指的都是最多能容纳的 token 数。

一次生成的完整流程

1

接收输入：系统提示 + 对话历史 + 新消息 + 可能附带的检索文档，全部拼接为输入序列。

2

切 Token：把文本切成 token 序列；若超出窗口上限，会被截断（通常是丢弃最早/最远的历史）。

3

喂进模型：整段进入 Transformer，通过自注意力让各 token 互相建立关联、携带彼此信息。

4

逐词生成：模型每次只预测"下一个 token"，依据的是当前全部上下文 + 它刚生成的词。

5

回写历史：新生成的话被追加进历史，作为"下一轮"上下文的一部分继续滚动。

最小 walk-through 示例 🧪

假设窗口 = 4K tokens，对话推进：

  1. 你贴入一篇约 3K tokens 的文档，问"总结要点"。 → 3K 资料 + 你的问题 ≈ 3.2K，在窗口内，正常回答。
  2. 你又问了 20 轮，历史膨胀到约 5K tokens。 → 超出 4K 上限，系统从最早的历史开始截断，只保留最近约 4K。
  3. 现在问"我们最开始那篇文档的第 2 节讲了啥？" → 那部分已被裁掉，模型答不上来。

结论：模型不是"忘了"，而是那部分内容因为没进入当前上下文而不存在——这正是"上下文"与"记忆"的根本分野。

缓解长文的常见工程手段

  • 检索增强（RAG）：不整篇塞入，而是先检索相关片段再放进上下文。
  • 摘要/压缩历史：把旧轮次压成几句摘要保留。
  • 长上下文模型：用 128K~1M 窗口直接容纳更多内容。

03应用场景 Use Cases

长文档处理 高频

直接喂入整份论文/合同/代码库做问答。解决"内容太长、放不下"的基础需求。

多轮对话助理 高频

客服/写作/编程对话。上下文承载前面聊过的事实与偏好，保证回答连贯。

系统提示词（System Prompt）

把角色、规则、工具说明写进上下文头部，约束模型行为。

检索增强 RAG 高频

把检索到的"相关知识块"注入上下文再让模型回答，兼顾新鲜与省 token。

工具/函数定义注入

把可用函数的 schema 放进上下文，让模型学会"申请调用哪个工具"。

Agent 多步记忆 进阶

把当前任务的状态、中间结果放回上下文，供自主循环持续参考。

何时该用 / 何时别硬用：需要模型"理解长文、跨多轮连贯"时充分用好上下文；但别用上下文当永久数据库——那是给记忆/检索系统的活。盲目加大窗口会显著抬高每轮成本与延迟。

04边界辨析 Boundary & Distinctions

与易混淆概念对比

维度上下文 Context记忆 Memory
本质本轮一次性喂给模型、可见可依赖的文本跨会话/跨轮的持久化信息（向量库、知识库等）
载体输入序列（token）外部存储，需要时再检索回填进上下文
有无上限受上下文窗口限制理论上可很大，但取用仍需回填
丢失表现超出即被截断、内容消失靠"检索没召回"而暂时取不到，非真消失

同样需要区分上下文窗口（容量）与"模型能不能有效利用全部窗口"（有效上下文）——研究（如 "Lost in the Middle"）表明模型对超长上下文的中部信息利用率偏低，别假设"放得下就一定会被用好"。

它不能做什么（局限性）

  • 不能主动跨会话记得你——除非产品把历史/记忆写回上下文。
  • 塞不进窗口的长内容若未截断策略保护，信息会被静默丢弃。
  • 超长上下文= 高 token 成本 + 更慢 + 中部信息被稀释，不是越大越好。

新手误区 / 直觉陷阱

  • 误区：模型"记得"上次聊了什么。其实是每轮都把历史逐字叠回上下文，它靠"重读"而非"记住"。
  • 误区：上下文按"字"算。按 Token 算，中文/英文/代码的 token 数差异很大。
  • 误区：窗口越大越好。大窗口带来成本、延迟与"lost in the middle"，关键内容应放头尾或显式强调。

06学习回顾自测 Quiz

1. 用自己的话解释：为什么模型关掉网页再打开，就"不记得"你上次聊了什么？
参考答案：因为模型没有原生持久记忆，它靠每一轮把"历史文字"重新放进上下文来"重读"。新会话没有把这些历史回填进上下文，它就看不到，自然答不上来——它不是忘了，是那部分根本没进它"当前可见的输入"。
2. 场景判断题：你贴了一篇 2000 字的文章，窗口是 4K token（约等于 3 千多汉字）。又问了一堆话把历史撑爆。问最早那篇的第 2 节，模型说"没提过"。原因最可能是？
参考答案：很可能是最早内容被截断丢弃了。历史超过窗口上限时，系统通常会裁剪最早的对话/文档，保留最近的 token。所以那不是模型"记性差"，而是那段内容已不在当前上下文里。
3. 深入理解题：既然窗口越大越好，为什么厂商还要做"截断历史/压缩摘要"而不是把所有东西都塞进去？
参考答案：三点：①成本与延迟随 token 数快速上升，每轮都要处理全部上下文；②超长上下文存在 "lost in the middle"，中间信息利用率低，硬塞反而稀释重点；③计算量随长度增长，超长输入会显著拖慢并抬高显存占用。因此好的设计是"分层记忆 + 检索 + 摘要"，用最小且高相关的上下文达到效果。
