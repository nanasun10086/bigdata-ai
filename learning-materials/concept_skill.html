Concept Learning Material · 03

Skill（技能）

在 Agent 世界里，"技能"是把"会做一件事的方法"封装成可复用、可被 AI 调用的说明书+工具包。本资料讲清它是什么、怎么运作、能干什么、别和什么搞混。

Prompt 工程可复用工具封装Agent 能力

01个人解释 Personal Explanation

一句话：Skill 是写给 AI 看的一份"做某事的完整操作手册"，可反复调用、随时唤醒。 普通提示词像"给 AI 的一句口头叮嘱"，这次说了下次还要再叮嘱一遍。而 Skill 是把"识别什么情况该用 + 具体怎么做 + 需要哪些参考资料/脚本"打包成一份标准化文件（通常叫 SKILL.md），AI 学会后会"看到相关需求就自动触发并照章执行"——相当于给 AI 装上了一张"职业技能证书"。

用人类世界打比方：招聘时你不会每次面试都重新发明"怎么面试"，而是有一套 SOP（标准作业流程）——什么岗位、问哪些问题、如何评分。Skill 之于 Agent，就是这个 SOP：把一次性的聪明沉淀为可重复的专业能力。

一个生活化类比 📋

想象你新雇了一位助理，他本身很聪明但什么行业知识都没有。你可以：
① 每次遇到一个流程都现场口述一遍（= 普通 prompt，费劲且易漏）；
② 把"如何做月报 / 如何订机票 / 如何写合同"各写成一份图文手册放在文件夹里，并告诉他"遇到这类活就翻对应手册照着做"（= Skill）。
选②，他才能独立、稳定、批量地帮你处理这些事。

个人倾向（可讨论）：Skill 最值钱的地方不是"多给 AI 几句提示"，而是把经验结构化、把动作脚本化、把知识可持续维护。但别神化它——它本质上仍是"提示 + 资料 + 脚本"的组合，输出质量取决于 Skill 写得好不好、以及底层模型的能力边界。好的 Skill 要边界清晰（何时用、何时不用），否则会像给了把锤子、看谁都像钉子。

02核心机制 Core Mechanism

以常见实现为例，一个 Skill 通常是一个目录 + 一份元数据说明书 + 可选附属文件。

典型文件结构

my-skill/
├─ SKILL.md        ← 核心：给 AI 的"操作手册"，含 YAML 元数据
├─ scripts/        ← 可选：可直接运行的脚本/工具
├─ references/     ← 可选：参考文档/模板/示例
└─ assets/         ← 可选：图片等素材

SKILL.md 的典型骨架

---
name: my-skill
description: 在"什么场景"下被触发（写给调度器/AI 判断是否调用）
---

# 我的技能
## 0. 角色与目标
## 1. 适用场景（何时触发、何时不触发）
## 2. 输入信息（必填/可选）
## 3. 执行步骤（Step1→StepN 的 SOP）
## 4. 输出/交付物
## 5. 自检/质量要求

它如何"被运行"

关键在于 description：当用户提出请求时，Agent/调度层会把已安装 Skill 的 description 与当前任务做匹配，命中则把对应 SKILL.md 全文加载进上下文，AI 据此"变身"成该领域的执行者，照章完成任务。就像一个技能触发器。

一个最小 walk-through 示例 🧪

假设装了一个"meeting-notes"技能（生成会议纪要）。

  1. 触发：你说"帮我把这段讨论整理成会议纪要，顺便发给同事"。其 description 含"会议纪要、整理讨论、参会人、行动项"等关键词 → 命中。
  2. 加载：系统把 meeting-notes/SKILL.md 全文读入上下文。
  3. 执行：AI 照手册要求：提取参会人→归纳议题→列决议→列行动项（责任人+截止）→格式化。
  4. 交付：产出一份规范纪要，并按其步骤调用发信工具发送。

关键：下次你再要纪要，不用重新教它格式——技能已记住"怎么干"。这就是 Skill 的复用价值。

核心组成一句话

  • 元数据 description → 决定"何时被唤醒"（触发匹配）。
  • 正文 SOP → 决定"具体怎么干"（稳定产出）。
  • 附属脚本/资料 → 决定"能不能真干活"（调用工具/本地能力）。

03应用场景 Use Cases

文档/报告生成 高频

把"写报告/纪要/合同"的固定规范封装成技能，保证格式与质量一致，省去重复交代。

专业领域问答 高频

把某领域的方法论（如"概念学习资料生成"）写成技能，AI 见需求即按方法论执行。

特定格式处理 高频

固定要求转表格/转 HTML/转 docx，用技能固化"输入→转换→输出"规则。

流程自动化

把多步操作（搜→整理→排版→发送）打包，让 AI 一键跑通。

团队共享最佳实践

把团队积累的经验固化成技能文件，供成员/Agent 复用，实现"知识资产化"。

何时该用 / 何时别硬用：当某类任务会反复出现、步骤相对稳定、值得统一标准时适合做 Skill；一次性/无固定章法的任务做成 Skill 反而增加维护负担。

它不能做什么（局限性）

  • Skill 不改变底层模型能力——模型不会、Skill 也教不会；它只是把"已知会做的步骤"稳定化。
  • 没有配套工具/接口的 Skill，"说明书再厚也无法真正执行外部动作"。
  • 依赖加载（把 SKILL.md 全文读入上下文），内容过长会挤占上下文、增加成本。

新手误区 / 直觉陷阱

  • 误区：Skill 能教会模型任何新知识。只能封装"可描述的步骤/规则"，无法凭空赋予模型不具备的推理或知识能力。
  • 误区：Skill = Tool。Skill 偏"流程方法"，Tool 偏"可执行接口"，两者不同层、常配合使用。
  • 误区：写一个 SKILL.md 就一劳永逸。质量差的 Skill（触发描述含糊、步骤不清）反而会误触发或产出不稳定，需像代码一样维护与测试。

06学习回顾自测 Quiz

1. 用自己的话解释：Skill 相比"每次都现场交代怎么做"，优势在哪？
参考答案：把"什么情况该用 + 具体步骤 + 参考脚本"固化成一个可被自动触发的标准文件后：①不用每次重复交代，节省沟通；②产出更稳定、标准统一；③可集中维护、版本管理、团队复用，把经验沉淀为资产；④可附带脚本实现真正执行而不只是"说"。
2. 场景判断题：某助手"会联网搜索（这是它的一个能力接口）"，与"按一套研报写作规范自动出研报"——哪一个更像 Skill？
参考答案：后者更像 Skill。联网搜索是可被调用的"工具/接口"；而"按研报规范自动出研报"封装了写作流程与触发条件，属于可复用技能。若该技能还调用搜索工具去取数，就是 Skill 内嵌 Tool 的典型配合。
3. 深入理解题：为什么说"Skill 并不能凭空增强模型能力"？那它的价值到底是什么？
参考答案：模型的能力天花板由其训练决定，Skill 只是把"既有能力"按固定、可靠的流程组织并触发，无法教会模型本身不掌握的东西。它的价值在于：①把不稳定的单次发挥变成稳定可复现的产出；②减少用户重复交代；③通过挂脚本/资料扩展可用范围（但这本质靠的是工具，不是给模型"灌知识"）。所以它是"组织与调用"层面的增益，而非"能力"层面的增益。
